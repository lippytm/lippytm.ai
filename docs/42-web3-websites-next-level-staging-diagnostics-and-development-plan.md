## Best Practices

### Platform Best Practices
- use one master platform instead of 42 disconnected site projects
- use shared components and site configuration profiles
- keep site identity configurable, not hard-coded everywhere
- make the platform registry-driven
- build once, vary many times

### Repository Best Practices
- treat repos as reference-resource providers
- map each repo to platform functions and site categories
- keep docs close to the resources they define
- turn repeated ideas into reusable modules
- maintain a resource registry and not just a list of repos

### AI Swarm Best Practices
- define swarm roles clearly
- keep swarm responsibilities narrow and composable
- have a QA/debug swarm review outputs from creation and implementation swarms
- use control tower logic for orchestration and visibility
- log decisions, fixes, and rerun improvements

### Website Best Practices
- one website = one primary role and audience emphasis
- keep a consistent shell with category-specific variation
- link intelligently to the rest of the ecosystem
- keep one primary CTA per key page
- make every page explain what it does, who it is for, and what to do next

### Diagnostics Best Practices
- diagnose by layer
- separate architecture errors from implementation errors
- separate copy issues from routing issues
- separate UX issues from infrastructure issues
- do not wait for perfection before creating staging artifacts

## Diagnostic Layers

### Layer 1 — Architecture Diagnostics
Questions:
- is the platform model clear?
- are responsibilities separated correctly?
- is the repo-to-platform relationship clear?
- are the 24 repo resource roles defined well enough?
- are the AI swarm roles non-overlapping enough?

Outputs:
- architecture gaps list
- unclear ownership list
- missing registry fields
- unresolved dependency list

### Layer 2 — Blueprint Diagnostics
Questions:
- do the docs agree with each other?
- are there contradictions in platform-first vs funnel-first logic?
- are the first 6 anchors defined clearly enough?
- is the 42-site map complete enough to implement in phases?

Outputs:
- doc inconsistency list
- missing spec list
- next-required-doc list

### Layer 3 — Component Diagnostics
Questions:
- do we know the component list for each anchor site?
- do we know the required shared components?
- do we know which components need AI agent support?
- do we know which components are global vs category-specific?

Outputs:
- missing components list
- duplicate concept list
- shared-package candidate list

### Layer 4 — Site Diagnostics
Questions:
- does each site have a clear purpose?
- does each site have a page structure?
- does each site have a primary CTA?
- does each site have related repo resources defined?

Outputs:
- incomplete site card list
- missing page list
- missing CTA list
- missing cross-link list

### Layer 5 — Flow Diagnostics
Questions:
- can a user understand the hub?
- can a user get routed to the correct site?
- can a user find an offer?
- can a user build, buy, or customize?

Outputs:
- broken journey list
- friction list
- over-complexity list

### Layer 6 — Operations Diagnostics
Questions:
- do we know how updates flow?
- do we know how deployments will be staged?
- do we know what maintenance means per site?
- do we know how QA gets triggered?

Outputs:
- missing ops process list
- deployment gap list
- missing monitoring list

## Debugging Categories

### 1. Concept Debugging
Used when the idea itself is unclear, too broad, duplicated, or contradictory.

### 2. Architecture Debugging
Used when system responsibilities are mixed or the platform model is incomplete.

### 3. Content / Copy Debugging
Used when promises, offers, headlines, or page explanations are weak.

### 4. UX Debugging
Used when users cannot find what they need or are overwhelmed.

### 5. Logic / Routing Debugging
Used when site-to-site movement, offer mapping, or category logic is broken.

### 6. Implementation Debugging
Used when code, components, forms, or integrations do not work.

### 7. Operations Debugging
Used when deployment, maintenance, QA, or versioning is weak.
